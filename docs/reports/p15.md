## 1. SCOPE AND GOALS

The platform declares its expectations in `data_contracts/*.yml`
(14 contracts), but *enforces* them through hand-written Python in three
layers:

| Layer | File | Duplicated knowledge |
|-------|------|----------------------|
| Bronze quality gate | `src/mri/ingestion/quality.py` | `_declared_specs` (one `add(...)` per source) + `REFERENCE_COLUMNS` |
| Bronze standardization | `src/mri/ingestion/bronze_schema.py` | `PARTITION_COLUMNS` (date partition per fact source) |
| Silver DDL/loader | `src/mri/silver/ddl.py` | `SOURCE_TABLES`, `PG_TYPES`, `PROVENANCE_COLUMNS` |

An edit to one of those places without the others silently broke a contract.
Goals: (1) treat the contract as the source of truth; (2) detect every drift
class the phase names without false positives; (3) wire the check into the
test suite/CI; (4) write the governance doc + ADR.

## 2. CONTRACTS AS THE SOURCE OF TRUTH — INVENTORY OF DUPLICATED KNOWLEDGE

| Contract promise | Implementation | Drift risk |
|------------------|----------------|------------|
| `quality.declared` range/set/pair/regex lines | `_declared_specs` hard-codes each rule per source id | a rule on one side only |
| `X exists in Y` referential lines | `REFERENCE_COLUMNS` source → (dim, column) table | set/column divergence |
| Volume, not-null, types, key uniqueness | `_generic_specs` — derived from the contract itself | **cannot drift** (single source) |
| Bronze date partitioning | `PARTITION_COLUMNS` (`sales→sale_date`, `purchases→purchase_date`, `inventory→snapshot_date`) | renamed/dropped partition column |
| Source → Silver table | `SOURCE_TABLES` (14 sources → 13 tables; two weather contracts merge into `weather`) | unmapped or orphaned id |
| Column renderability + reserved names | `PG_TYPES`, `PROVENANCE_COLUMNS` appended to every Silver table | unrenderable type / provenance clash |

## 3. THE CANONICAL RULE MODEL

The detector maps **both** the declared text and the runtime expectations
onto one rule vocabulary, so comparison is semantic, never textual:

| Kind | Declared example | Runtime expectation |
|------|------------------|---------------------|
| `uniqueness` | `sale_id is unique and not null` / `date, base and quote are unique and not null` / `composite key (snapshot_date, store_id, product_id) is unique` | generic primary-key + not-null (checked against `keys.primary` and column nullability) |
| `between` | `amount between 0 and 100` / `rate > 0` / `launch_date <= 2024-12-31` / `net_amount_mad >= 0 and margin_mad >= 0` (compound → 2 rules) | `ExpectColumnValuesToBeBetween` |
| `set` | `channel_type in {physical, digital}` | `ExpectColumnValuesToBeInSet` |
| `regex` | `external_product_id matches ^[0-9]{8,14}$` | `ExpectColumnValuesToMatchRegex` |
| `pair` | `end_date >= start_date` / `unit_price_mad >= unit_cost_mad` | `ExpectColumnPairValuesAToBeGreaterThanB` |
| `referential` | `store_id exists in stores` | `REFERENCE_COLUMNS` → set expectation (resolved statically) |

Grammar tolerance (no false positives): `is between`/`between`, `is/are
unique and not null`, `composite key (...)`, compound `X >= a and Y >= b`,
sorted set membership, and regex `\d` ≡ `[0-9]` normalisation.

## 4. DIRECTION A — DECLARED BUT NOT IMPLEMENTED

Every canonical rule parsed from `quality.declared` must have a counterpart:
a `between`/`set`/`regex`/`pair` rule must match one of the expectations that
`build_specs` actually generates for that contract (introspected in memory on
a skeleton frame — no GX execution, no database); a `referential` rule must
appear in `REFERENCE_COLUMNS`; a `uniqueness` rule must agree with the
contract's own `keys.primary` and nullability (the generic expectations
derive from those). A rule with no counterpart → `declared_not_implemented`.

## 5. DIRECTION B — IMPLEMENTED BUT NOT DECLARED

Symmetric: every declared-type expectation produced by `_declared_specs`, and
every `REFERENCE_COLUMNS` entry, must trace back to a documented `quality.declared`
line. This catches an engineer hard-coding a rule in `quality.py` and never
publishing it in YAML (`implemented_not_declared`) — the runtime being stricter
than the published contract is a contract violation too. Generic expectations
are contract-derived, so they are excluded from this pass by design.

## 6. REFERENTIAL RULES

Referential checks are skipped or materialised depending on runtime reference
data (`add_reference`), so drift there is detected **statically** against
`REFERENCE_COLUMNS` in both directions. Verified inventory (Phase 15):
`customers→(regions.region_id, channels.preferred_channel_id)`,
`open_meteo_forecast/history→regions.region_id`,
`promotions→products.product_id`, `purchases→(stores.store_id,
products.product_id)`, `sales→(stores.store_id, products.product_id,
channels.channel_id)`, `stores→regions.region_id` — every declared
`exists in` line matches its entry and vice-versa.

## 7. SOURCE MAPPING

- `set(contracts) ⊆ set(SOURCE_TABLES)` else `source_mapping_missing`
  (contract without a Silver home).
- `set(SOURCE_TABLES) ⊆ set(contracts)` else `source_mapping_orphan`
  (map entry with no contract file).
- Documented exception: `BRONZE_ONLY_SOURCES` (currently empty — all 14
  sources land in Silver; the four external APIs map to
  `weather`/`fx_rates`/`external_products`). A bronze-only source in that set
  warns instead of failing.
- The reverse check fires correctly today because `silver/ddl.py`
  `build_table_specs` already raises on unknowns at load time; the detector
  makes the same guarantee visible in CI without a database.

## 8. VERSION SEMANTICS

`_check_versions` reads each file's `id`/`version` directly:

- non-semver (`1.0`, `abc`) → `version_mismatch`;
- `MAJOR != SUPPORTED_CONTRACT_MAJOR (=1)` → `version_mismatch`;
- the **same contract id in two files** → `version_mismatch` (a contract
  version is immutable once released, so two declarations are a conflict).

`_parse_contract` already enforces semver+major on load; the light pass makes
the same violation a reviewable report entry instead of a bare exception.

## 9. UNSUPPORTED COLUMNS

Per contract column the detector verifies: (a) no name collides with the Silver
provenance columns (`source`, `source_file`, `source_hash`, `batch_id`,
`ingestion_run_id`, `ingestion_timestamp`) — `_merge_columns` would abort the
load; (b) the type is renderable in `PG_TYPES`; (c) for `PARTITION_COLUMNS`
sources, the partition column still exists in the contract.

## 16. WARNINGS AND LIMITATIONS

- **The rule vocabulary is finite.** A genuinely new rule idiom must first be
  taught to the classifier or it reports as an unclassifiable **warning**
  (never a crash, never a false pass).
- **Regex equivalence is token normalisation** (`\d`→`[0-9]`), not full regex
  semantics — belt, not suspenders.
- **Partial-directory probes** must scope `source_tables` to the inspected
  set, or unrelated `SOURCE_TABLES` entries look like orphans (documented in
  the governance doc and shown in the tests).
- **Carry-over:** Phase 14's *live* verification (incremental integration
  suite + 100K/1M benchmarks) remains gated on the missing local `.env`; it
  does not block Phase 15, which needs no live stack.
