Scope: prove that the documented project starts and runs on a **clean local
environment without hidden workstation state**, using a **non-destructive,
isolated scratch stack** (separate Compose project, temporary env file, unique

## 1. OBJECTIVE

Validate clean-install reproducibility end to end (compose config → images →

## 2. ISOLATION METHOD

The base Compose file hardcodes `name: mri`, explicit `container_name: mri-*`,
explicit volume `name: mri-*-data` and network `name: mri-net`. A different
`-p` project name alone therefore does **not** isolate them. Isolation was
achieved with a throwaway override composed on top of the four repository files:

- **Project name** `mri-cs` (both `-p mri-cs` and `name: mri-cs`).
- **Unique container names** `mri-cs-*` (override `container_name` on every
  service, including the ones without one in the base files).
- **Unique named volumes** `mri-cs-postgres-data`, `mri-cs-minio-data`,
  `mri-cs-airflow-postgres-data`, `mri-cs-superset-home` (+ declared
  `mri-cs-prometheus-data` / `mri-cs-grafana-data`).
- **Unique network** `mri-cs-net` (bridge).
- **Unique host ports** via a temporary `--env-file`.
- **Re-tagged project images** `mri-cs-airflow:3.3.2`, `mri-cs-superset:6.1.0`,
  `mri-cs-metrics:0.1.0`, so building here could never overwrite the normal
  `mri-*` images.
- **Temporary env file** built by copying the repository `.env` and overriding
  only the endpoints/ports.
- **Temporary data folder** outside the repo for the generated dataset.

Verification: `docker compose … config` resolved **`name: mri-cs`**, only
`mri-cs-*` container/volume names, and **0** non-`mri-cs` names (leak check).

Why an isolated stack instead of a destructive `down -v`: the existing database
and MinIO volumes hold the live state and must survive, so a **new** stack —
not the user's — was provisioned and destroyed.

## 3. CLEAN-START COMMANDS

Ports used by the scratch stack (all verified free; different from the normal
stack): PostgreSQL `5543`, Airflow metadata `5544`, MinIO API/console
`9100`/`9101`, Airflow `8180`, Superset `8188`, metrics `9345`, Prometheus
`9190`, Grafana `3401`.

```powershell
# 0. scratch env + override live OUTSIDE the repo (temporary):
#    %TEMP%\opencode\p26\clean.env            (copy of .env with overridden ports)
#    %TEMP%\opencode\p26\compose.override.yml (unique names/volumes/network/ports)

$env_ = "$env:TEMP\opencode\p26\clean.env"
$ov   = "$env:TEMP\opencode\p26\compose.override.yml"
$files = @(
  '-f','infrastructure/docker/docker-compose.yml',
  '-f','infrastructure/docker/docker-compose.airflow.yml',
  '-f','infrastructure/docker/docker-compose.superset.yml',
  '-f','infrastructure/docker/docker-compose.observability.yml',
  '-f',$ov)

# 1. validate the isolated configuration
docker compose -p mri-cs --env-file $env_ @files config

# 2. base services
docker compose -p mri-cs --env-file $env_ @files up -d postgres minio

# 3. pipeline (host-side; scratch env exported into the shell first)
uv run python -m apps.data_generator --scale tiny --seed 42 --output "$env:TEMP\opencode\p26\data"
uv run python -m apps.ingestion validate --path "$env:TEMP\opencode\p26\data\tiny" --recursive
uv run python -m apps.ingestion ingest   --path "$env:TEMP\opencode\p26\data\tiny" --recursive
uv run python -m apps.ingestion bronze   --source all
uv run python -m apps.ingestion load     --source all
uv run python -m apps.warehouse build
uv run python -m apps.dbt build

# 4. Airflow overlay (DAG reads data/generated/tiny from the repo mount)
docker compose -p mri-cs --env-file $env_ @files up -d airflow-postgres airflow-init airflow-apiserver airflow-scheduler airflow-dag-processor
docker exec mri-cs-airflow-scheduler airflow dags unpause morocco_retail_pipeline
docker exec mri-cs-airflow-scheduler airflow dags trigger morocco_retail_pipeline

# 5. Superset overlay + read-only role + seed/verify
docker compose -p mri-cs --env-file $env_ @files up -d superset-init superset
Get-Content infrastructure/sql/bi-reader-readonly.sql | docker exec -i mri-cs-postgres `
  psql -U retail_app -d retail -v ON_ERROR_STOP=1 `
  -v reader_user="$env:BI_READER_USER" -v reader_password="$env:BI_READER_PASSWORD" -f -
$env:SUPERSET_URL = "http://localhost:8188"
uv run python dashboards/superset/seed.py all
uv run python dashboards/superset/verify.py

# 6. teardown — scratch ONLY
docker compose -p mri-cs --env-file $env_ @files down -v --remove-orphans
docker rmi mri-cs-airflow:3.3.2 mri-cs-superset:6.1.0 mri-cs-metrics:0.1.0
```

## 17. WARNINGS

1. **Host RAM.** The 3.73 GiB Docker VM cannot run the normal stack and a second
   full stack simultaneously; the Airflow overlay must be tested with the other
   stack stopped (services are started in groups — as the README already notes).
2. **Disk.** The audit consumed ≈ 5 GiB of host disk; the Docker Desktop VHDX
   does not shrink automatically after image deletion, and the build cache
   (≈ 6.9 GiB reclaimable) was intentionally not pruned.
3. **README gap (fixed).** The Quick start omitted the mandatory read-only BI
   role creation; a fresh clone following the old steps would fail at
   `superset-seed`.
4. **Shared bind mounts.** `airflow/logs` is bind-mounted from the repo, so
   scratch-run logs are interleaved with existing daily logs under the same path.
5. **Dataset figure drift.** A clean `tiny/seed42` build yields **net revenue
   86,404.90** over **2,000** `fact_ventes` rows, whereas the previously reported
   live figure was **108,770.18** over **1,818** rows — the live database
   evidently holds a different/accumulated dataset than a fresh tiny run. This is
   not a pipeline defect but should be reconciled by the owner.
6. **Transcript hygiene (carried over).** An earlier `docker inspect` exposed
   Airflow Fernet/JWT values in a transcript; rotating
   `AIRFLOW__CORE__FERNET_KEY` and `AIRFLOW_JWT_SECRET` remains advisable.
