## 1. OBJECTIVE

Deliver a **unified operational audit model**: every pipeline operation,
across all six layers, emits one canonical structured event; all events land
in one append-only JSONL log that is queryable offline and mirrored into a
PostgreSQL `ops` schema; reliable metrics (stage success/failure rates,
durations, row counts, freshness) and full DAG-run correlation are derived
from that single source — with **no second bespoke audit system** and
**no disturbance** to the existing pipeline behaviour (392 unit tests pass;
library callers only gained an optional, backward-compatible `run_id`).

## 2. LOGGING DESIGN

- **One schema, one order, everywhere.** `PipelineEvent`
  (`src/mri/observability/events.py`) fixes 15 fields in one order:
  `timestamp, run_id, dag_run_id, pipeline, stage, source, batch_id, status,
  duration_ms, records_read, records_written, records_rejected, error_code,
  message, payload`. The same names/order appear in the JSONL line, the
  console JSON, the `ops` table and the `ops` views. `pipeline` ∈
  {ingestion, bronze, silver, warehouse, dbt, airflow}; timestamps are UTC
  ISO-8601 with microsecond precision; `payload` is free-form JSON.
- **`error_code` vocabulary** is stable and machine-readable:
  `VALIDATION_FAILED`, `INGEST_REJECTED`, `EXTERNAL_FAILED`, `BRONZE_FAILED`,
  `SILVER_LOAD_FAILED`, `WAREHOUSE_UNBALANCED`, `DBT_FAILED`,
  `DBT_MODEL_FAILED`. `DBT_MODEL_FAILED` is stamped **only** on models whose
  `run_results.json` status is `error`/`fail`; `success`, `pass` and
  `skipped` models emit no error code (regression-tested).
- **One JSONL sink, always available.** `EventLog` appends compact JSONL to
  `reports/observability/events.jsonl` (override:
  `Settings.observability_dir`, env `MRI_OBSERVABILITY_DIR`,
  `--observability-dir`); plain text, append-only, offline-safe — a crash
  leaves a `started` marker, and corrupt lines are skipped on read.
- **Secrets never logged.** `redact()` masks credential-looking payload keys;
  CLIs never pass credentials to the staging code.
- **Console JSON is opt-in** (`MRI_JSON_LOG_CONSOLE=1`) and writes to
  **stderr** only; the JSONL file stays the canonical sink.
- **Emission point = CLI boundary.** Library pipelines gained an optional
  `run_id` keyword and stay observable-agnostic. `apps.dbt` intercepts and
  strips its correlation flags so dbt itself never receives them.
- **Correlation context.** Every CLI stamps a process-wide context from
  `--dag-run-id` / `--observability-dir` before delegating to the staging
  code, so a single run's events all carry the same ids.

## 3. AUDIT MODEL

- **`ops.pipeline_event`** is the run/event-level record across all stages:
  one column per canonical field + identity `event_id`, `event_hash TEXT NOT
  NULL`, `payload JSONB`; unique index on `event_hash` (idempotent `INSERT …
  ON CONFLICT DO NOTHING`), indexes on `dag_run_id`, `run_id`,
  `(pipeline, stage, timestamp)`, `batch_id`. `apps.observability sync` bulk
  loads the JSONL (payload as `%s::jsonb`), so offline and SQL never diverge.
- **`audit.load_audit`** keeps its batch-level role as the registry of record
  for every Silver load (unique successful `(batch_id, target_table)`). It
  joins onto `ops.pipeline_event` on `run_id` / `batch_id` — one model, no
  migration, no duplicated storage.
- **Correlation contract.** One `dag_run_id` spans every stage of one
  orchestrated run; one `run_id` is generated **before** the run and threaded
  (a crashed run still leaves `started`-only events and is counted failed);
  `batch_id` threads lineage (raw filename stem → Bronze batch → Silver batch
  → warehouse subset → dbt model).
- The three views are `CREATE OR REPLACE VIEW`, so re-sync never drops.

## 4. METRICS

Definitions are **identical offline and in SQL** (`metrics.py` is a pure
function over events; `ops.v_run_facts` reproduces it), verified live:

- **Run outcome** — failed if any event failed; else success only when the
  chronologically last event status is `success`. A run whose last event is
  non-terminal (crash) ⇒ **failed — crashes surface in the failure rate**.
- **Row counters** — summed only over granular (`batch_id <> ''`) events so
  summaries never double-count (live check: silver `rows_written=9185` and
  warehouse `13013` equal the exact per-batch sums).
- **Duration** — explicit `duration_ms` when present (measurement at run
  start/finish), else the span between first and last stored event.
- **Freshness** — per source, age of the newest successful event
  (`now() − last_successful_at`).
- Offline/SQL parity proven against the real log (544 events, 60 runs):
  bronze 16 runs / 62.50% success and dbt 2 runs / 0.00% success match on
  both surfaces, including the crash-count and failed-dbt-run cases.

`reconcile` emits the DAG-level terminal event

scheduler: `--dag-run-id` is just a string the orchestrator supplies.

## 14. WARNINGS

- **Staged environments** with pre-Phase-14 `dbt_marts.fact_*` tables must
  be migrated (drop + full rebuild) before adding the Phase-14 incremental
  watermark; the fresh-DB CI path never hits this. The live failure was
  caught exactly because the trace is now observable.
- The first successful dbt rerun's per-model events predate a small code
  fix and still carry `DBT_MODEL_FAILED` on `pass`/`skipped` records in the
  stored log; the fix (§2) is in place and unit-tested, so newer runs emit
  correct codes. Historical log lines are left as recorded.
- Row counters are per stage and counted once per stage; cross-stage
  lineage totals require joining on `run_id`/`batch_id`.
- `ops` mirror checked only at sync time; long-running deployments with
  many runs may want a size-capped JSONL rotation (see §18).

## 18. RECOMMENDATIONS

1. **Keep the phase rule:** no new event-emitting code inside library
   pipelines; new CLIs emit at the boundary and reuse the threaded `run_id`.
2. **Treat `ops.pipeline_event` as the long-term store** and the JSONL as
   the always-available feed; size-cap and archive the JSONL.
3. **Expose `ops` views to the BI read-only role** so Superset/analysts get
   metrics and freshness without touching the JSONL.
4. **Extend the metric vocabulary** (freshness alerting, time windows) in
   SQL only — the offline and SQL surfaces must stay definition-identical.
5. Similarly sign off **Phase 14 live runs** once the integration suite is
   executed, since they share the now-provisioned `.env` path.
