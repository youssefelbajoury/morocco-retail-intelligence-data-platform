# Phase 18 — Data lineage (completion report)

## OBJECTIVE
Make the platform able to answer, for every dataset, **where it came from and
what depends on it**, end to end: external/internal source → file ingestion →
RAW → Bronze → Silver PostgreSQL → dbt models → warehouse tables → Superset
datasets/dashboards. Reuse existing identifiers (source, file/object key,
SHA-256, batch id, run id, Airflow DAG run id, dataset, job, timestamp, status).
Evaluate OpenLineage **without upgrading the stack** and **without making a new
high-memory service mandatory**. Label every edge by the strength of its
evidence so design-time diagrams are never passed off as runtime lineage.

## LINEAGE APPROACH
- **Derived read-only view** in `src/mri/lineage/`: reads existing manifests,
  observability events and configuration; writes nothing to Postgres/MinIO/dbt.
- **Evidence kinds** (`observed` > `inferred` > `declared` > `unavailable`),
  strongest wins per `(upstream, downstream, job)`:
  - *declared* — from `SOURCE_TABLES`, dbt `manifest.json` `parent_map`, warehouse
    load SQL, Superset seed; *observed* — from the audit surface (events +
    manifests + `run_results.json`); *inferred* — declared dbt edge whose child
    actually executed; *unavailable* — input referenced but never produced.
- **Correlation** by `--dag-run-id` (and run/batch ids already in the evidence).
- **Extraction, not duplication:** dbt graph comes from the artifact; warehouse
  joins from the emitted SQL; Superset from an `ast` parse of `seed.py`.
- Minimal spec-shaped **OpenLineage RunEvent** emitter (JSONL) with stable
  UUIDv5 run ids and `parent` facets; no provider installed, no backend required.

## DATASETS COVERED
Layers and namespaces: `source` (`file:`/`api:`/`source:`), `raw` (`minio:`),
`bronze` (`minio:`), `silver`/`dbt`/`warehouse` (`postgres:`), `bi`
(`superset:`). Real run covered all seven layers: 28 source, 98 raw, 474 bronze,
13 silver, 167 dbt, 11 warehouse, 9 bi datasets.

## AIRFLOW INTEGRATION
No pipeline change: lineage consumes the `--dag-run-id` correlation that every
DAG task already passes (ADR-013). A review of `airflow/dags/morocco_retail_pipeline.py`
confirms each Bash task carries `--dag-run-id "{{ dag_run.run_id }}"`; the run
bookend event is reused as the run context. Emitted OpenLineage run events carry
a `parent` facet pointing at the DAG run so the external graph stays correlated.

## DBT INTEGRATION
`manifest.json` `parent_map` gives the model DAG (sources resolved via
`source_name`, models via the base `config['schema']`, `test.*` skipped);
`run_results.json` and `dbt` observability events mark which nodes actually ran,
turning matching declared edges into `inferred`. Job name `dbt.<model>`. A real
`dbt build` regenerated both artifacts with the unsuffixed base schema, so
dataset ids are stable (`postgres:dbt_marts.fact_ventes`).

## OPENLINEAGE EVENTS OR RECORDS
`reports/lineage/openlineage.jsonl` — 32 RunEvents for the evidence run: one per
observed job run (ingest, external, bronze, silver.load, warehouse.load) plus
one per executed dbt node. Each has `eventType`, ISO timestamp, `run`
(UUIDv5-stable id + Airflow parent facet), `job` (namespace `mri`, name), and
input/output `Dataset` facets (`minio://<bucket>` / `postgres://retail`).
`schemaURL = https://openlineage.io/spec/2-0-2/OpenLineage.json#/definitions/RunEvent`.

## REAL RUN EVIDENCE
Controlled real run `dag__lineage_20261010T182400` over `data/generated/tiny`:
ingest (10 already-ingested files), external (live open-meteo + frankfurter),
bronze, silver load, warehouse build, `dbt build` **PASS=167 / ERROR=0**. Then:

```
uv run python -m apps.lineage build --dag-run-id dag__lineage_20261010T182400

  edges_by_kind={"observed":617,"inferred":45,"declared":56,"unavailable":64}
  datasets_by_layer={"source":28,"raw":98,"bronze":474,"silver":13,
                     "dbt":167,"warehouse":11,"bi":9}
```

`trace --dataset postgres:warehouse.fact_ventes --direction upstream` walks back
through warehouse → silver → bronze markers → raw objects → source files/APIs.
The 64 `unavailable` inputs are genuine partial-run gaps: 55 `raw_external` + 8
`raw` objects present in Bronze from earlier runs but not re-ingested in this
DAG run, plus `audit.load_audit`.

## DEPENDENCIES ADDED
None. No `pyproject.toml`/`uv.lock` change. OpenLineage is emitted via the Python
stdlib (`json`, `uuid`); no `apache-airflow-providers-openlineage`,
`openlineage-python` or Marquez.

## DATABASE CHANGES
None. `apps.lineage build` is read-only against Postgres and MinIO; no DDL, no
new schema/tables. (The dbt build wrote its own models as part of the normal
pipeline, not for lineage.)

## RESOURCE IMPACT
Lineage build is an offline, single-process pass over local files: seconds of
CPU and a few MB of RAM; no new service, no container, no network. The deferred
Marquez alternative — a JVM service plus database — would be a persistent
high-memory component and is explicitly not adopted.

## WARNINGS
- `unavailable` edges are expected for partial/replayed DAG runs; they are
  reported, not hidden.
- Superset lineage is design-time (`declared`) because no dashboard query log
  exists.
- `reports/lineage/*` are operational artifacts and are not committed.

## RECOMMENDATIONS
- Schedule `apps.lineage build --dag-run-id {{ dag_run.run_id }}` as the last
  DAG task so every orchestrated run ships a correlated lineage snapshot.
- Ship the generated Mermaid per run as a report artifact for review.
- When a real backend is justified, point it at the existing emitter rather than
  re-instrumenting the pipeline.
- Treat a growing `unavailable` set as a data-completeness signal worth alerting
  on.
