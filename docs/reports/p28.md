### B.5 Tooling caveat (documented deviation)

Both official CLI password resetters — `airflow users reset-password --password`
and `superset fab reset-password --password` — **reported success but produced no
working credential** (login still failed; the stored hash did not verify against
the supplied password). The workaround that **works** is to set the hash directly
with Werkzeug's `generate_password_hash`:

- **Airflow:** via `airflow.providers.fab.auth_manager.models.User`, committed
  through `airflow.settings.Session`.
- **Superset:** via SQLite `ab_user.password` in `/app/superset_home/superset.db`.

The Airflow auth path (`POST /auth/token` → `FabAuthManager.create_token` →
`security_manager.auth_user_db`) and the Superset path (`POST
/api/v1/security/login`) then both succeed. This deviation is recorded because a
future operator following only the CLI would be misled.

## D. Réconciliation des données — Data reconciliation

### D.1 The two figures

| Figure | Source | Rows | Net revenue |
|--------|--------|------|-------------|
| Documented clean baseline | `tiny` / seed 42, current code | 2,000 | **86,404.90 MAD** |
| Live dashboards / warehouse | running `mri-*` stack | 2,000 | **120,265.53 MAD** |

(The earlier note of "1,818 rows / 108,770.18 MAD" corresponds to a **still
earlier** DB state and is not reproducible from the current raw bucket.)

### D.2 Root cause — proven, not a bug

The live `warehouse.fact_ventes` and `silver.sales` are **internally consistent**
(parity is exact: 120,265.53 == 120,265.53). The mismatch is between the live DB
and the current on-disk/generated dataset, and it is a **data-provenance /
idempotency artifact**:

1. Three distinct `tiny` generations exist as raw objects in MinIO
   (`retail-raw`, prefix `raw/sales/`):

   | Raw object | Bytes | Rows | Net revenue |
   |------------|-------|------|-------------|
   | `sales__17b2da95f48454ac.csv` (current code / on disk now) | 187,590 | 2,000 | **86,404.90** |
   | `sales__ba61595ae19e7ffe.csv` | 187,007 | 2,000 | **79,746.48** |
   | `sales__4bf38de602847d22.csv` (**what the warehouse holds**) | 188,532 | 2,000 | **120,265.53** |

2. All three share the **same natural keys** (`sale_id` = `S000000000…S000001999`)
   but different values, so successive Silver loads **upsert over one another**
   (last-writer-wins).
3. `audit.load_audit` records the load order:

   | Load date | Batch | Rows inserted |
   |-----------|-------|---------------|
   | 2026-10-07 | `sales__17b2da95f48454ac` | 2,000 |
   | 2026-10-09 | `sales__ba61595ae19e7ffe` | 2,000 |
   | **2026-10-14 08:23** | **`sales__4bf38de602847d22`** | **2,000** |

   → The last successful upsert (`4bf38de6`, 120,265.53) is what the warehouse and
   dashboards display.
4. The current generator (verified by re-running `python -m apps.data_generator
   --scale tiny --seed 42`) reproduces `17b2da95` = **86,404.90**, byte-for-byte
   identical to `data/generated/tiny/sales/sales.csv` on disk.

**Conclusion:** the dashboard KPI is *stale relative to the current baseline*, not
wrong. The pipeline computed it correctly from the last-loaded batch.

### D.3 Idempotency caveat (worth recording)

Because the current on-disk dataset (`17b2da95`) is **already registered** as a
loaded batch, a normal DAG re-run will be **skipped** for both ingest and load and
will **not** refresh the warehouse. Aligning the live stack with the 86,404.90
baseline therefore requires an explicit action (re-load the current dataset,
regenerate under a new content hash, or rebuild Silver/Warehouse) — all of which
**mutate live data** and were deliberately **not** performed in this read-only
phase.

### D.4 Disposition

- **Documented** (this section + `docs/limitations-and-roadmap.md` context).
- **Deferred** to an owner-authorized follow-up (§I): re-run the pipeline from the
  current `data/generated/tiny` so the live dashboards match the deterministic
  baseline, or accept the live figure as "the last loaded dataset".
