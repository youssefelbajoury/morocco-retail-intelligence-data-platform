# Phase 20 — Security & hardening (completion report)

## 1. OBJECTIVE

Audit and harden the platform's security posture: credential handling, database
least privilege, Apache Airflow and Superset defaults, container exposure,
supply chain (images/dependencies), and reproducibility of the object store.
Produce regression tests and documentation, then leave the stack running and
verified. Scope is a **host-local development deployment** — this is a
defensible hardening pass, not a production certification.

## 2. SCOPE AND THREAT MODEL

- **Trust boundary**: one Windows 11 host + Docker Desktop; a single private
  bridge network (`mri-net`). Container-to-container and host access are
  trusted; nothing is bound beyond loopback.
- **In scope**: secrets at rest/in git, DB privileges, auth/debug defaults,
  published ports, vulnerable/removed images, dependency CVEs.
- **Out of scope**: OS hardening, TLS, multi-host scaling, public exposure.
  The platform must not be exposed to the internet.

## 3. SECRETS

- Heuristic scan (`scripts-ignored/scan_secrets.py`, redacted output) over the
  working tree and `HEAD`: **only benign/placeholder hits**, no credentials.
- `.env` is git-ignored (`.gitignore`) and untracked (`git ls-files .env` →
  empty). `.env.example` carries placeholders only and documents every required
  Compose key.
- No password/key literals in compose files, Dockerfiles, DAGs or application
  code; all secrets flow through env vars.
- **Fix**: the real `.env` had been truncated to 13 keys, so Compose could not
  interpolate several `AIRFLOW_*`/`SUPERSET_*`/`BI_READER_*` values. The missing
  keys were **restored with freshly generated values** (hex for passwords,
  base64 for Fernet/JWT/secret), and the `airflow` metadata and `superset_bi`
  passwords were re-synced via `ALTER ROLE` to match.

## 4. DATABASE PRIVILEGES

Two deliberately separate PostgreSQL instances: `mri-postgres` (warehouse
`retail`) and `mri-airflow-postgres` (Airflow metadata only).

| Role | Finding |
|------|---------|
| `retail_app` (pipeline/dbt) | **is a SUPERUSER** — documented gap, not changed |
| `superset_bi` (BI reads) | LOGIN, **not** superuser, no CREATEROLE/CREATEDB, **no role memberships**, USAGE (not CREATE) on `warehouse`/`dbt_marts`/`audit`, **SELECT-only** table grants, `allow_dml=False` at the Superset layer |

Verified live: `superset_bi` reads `warehouse.dim_date` (1461 rows),
`dbt_marts.fact_ventes` (2000 rows), `audit.load_audit`, and its `CREATE TABLE`
is refused (`permission denied for schema public`). Grants are provisioned
idempotently by `infrastructure/sql/bi-reader-readonly.sql`.

## 5. APACHE AIRFLOW

- `AIRFLOW__CORE__FERNET_KEY` (valid, 44-char) and `AIRFLOW__API_AUTH__JWT_SECRET`
  supplied via env; the metadata DB holds **0 connections and 0 variables**
  (no ambient credentials at rest) and a single admin user.
- FAB auth manager; UI/API on `127.0.0.1:8080` only.
- DAG validated against the real Airflow `DagBag` (no secret literals).
- The compose overlay pins public resolvers (`8.8.8.8`/`1.1.1.1`) — a
  documented, measured mitigation for a Docker Desktop embedded-DNS outage;
  retained (see WARNINGS).

## 6. DOCKER / CONTAINER EXPOSURE

## 7. MINIO SUPPLY CHAIN (CVE-2025-62506)

MinIO community images were removed from Docker Hub and Quay (`denied` /
`no such manifest` on every tested tag). The previously pinned
`minio/minio:RELEASE.2025-09-07T16-13-09Z` is affected by **CVE-2025-62506**
(GHSA-jjjj-jwhf-8rgr, CVSS 8.1; Privesc via session-policy bypass), and its fix
release was never published as an image.

Adopted the maintained **Chainguard** rebuild, digest-pinned:

```
cgr.dev/chainguard/minio@sha256:dc455cdd4db6e390b1b26514f15ff37681a777bf8dab41aac445a0259f751e56
# RELEASE.2026-09-22T19-25-18Z (post-fix)
```

Validated in isolation (temp ports + creds) against the four MinIO
integration-test modules (6 passed) **before** adoption, then flipped in compose
(`user: "0:0"`, `/dev/tcp` healthcheck since the image has no curl), recreated
healthy (host HTTP 200), and the smoke test passed. The `mri-minio-data` volume
was snapshotted first (86.63 MB) and reused unchanged. CI's MinIO job was
converted from an unpullable `services:` container to a `docker run` step using
the same digest.

## 23. WHAT WAS ROTATED AND HOW

| Credential | Method | Verification |

| PostgreSQL `retail_app` | `ALTER ROLE retail_app WITH PASSWORD` (64-char) | new secret connects (dbt debug + psycopg on host and in the Airflow scheduler container, `current_user`=`retail_app`); previous secret rejected; `canlogin`/superuser preserved |

# PHASE 24 ADDENDUM — LEAST-PRIVILEGE POSTGRESQL ROLES (2026-10-14)

## 29. OBJECTIVE AND SCOPE

Remove the unnecessary SUPERUSER attribute from the application/login role
`retail_app` without breaking any pipeline, dbt, observability or BI operation;
keep `superset_bi` strictly read-only; validate on a disposable database before
touching the live cluster; add regression tests + docs; run the full gate. No
git commit/push, no volume deletes, no `.env` backup.

## 30. ROLE MODEL AND MIGRATION

Target model: a non-superuser **owner** application role (`retail_app`) plus an
otherwise-unused break-glass **SUPERUSER** (`retail_admin`). Ownership — not
SUPERUSER — is what the pipeline's DDL needs: warehouse/silver/observability/dbt
only create, alter and drop objects in schemas `retail_app` owns; no
`CREATE EXTENSION` is ever used and the only CREATEDB/CREATEROLE needs are
one-time provisioning.

Both documented constraints had to be worked around live:

| Constraint | Error | Work-around |
|------------|-------|-------------|
| Cannot strip SUPERUSER from the initdb bootstrap role (`retail_app`, OID 10) | `permission denied to alter role` / `The bootstrap user must have the SUPERUSER attribute` | Rename the bootstrap to `retail_admin` (keeps SUPERUSER) and create a fresh non-superuser `retail_app` (same password) |
| A role cannot rename its own session login | `session user cannot be renamed` | Perform the rename from a short-lived helper superuser session (dropped immediately after) |
| `REASSIGN OWNED` refuses the bootstrap role | `DependentObjectsStillExist: ... required by the database system` (413 system objects) | Move user objects explicitly (relations/functions/types/schemas); table-linked sequences cascade from their table |

`retail_app`'s password was kept identical, so no application/BI wiring changed;
only the new admin password was written to `.env`.

## 31. DISPOSABLE-DATABASE TEST

Created a throwaway database owned by a synthetic non-superuser login role
(`NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`) and ran: the
full DDL battery (schema/table/index/constraint/view/truncate/drop), denial of
`CREATE DATABASE`/`CREATE ROLE`, and the real pipeline (`apps.ingestion load
--source all --force` → `apps.warehouse build` → `apps.dbt build`), all exit 0.
Teardown clean. A second throwaway probe validated the exact ownership-transfer
SQL and confirmed indexes/sequences follow their table, and that the new owner
can write and drop.

## 32. LIVE MIGRATION RESULT

Applied after the disposable test:

1. dropped the leftover placeholder admin role;
2. renamed bootstrap `retail_app` → `retail_admin` via the helper session;
3. created non-superuser `retail_app` (same password);
4. `ALTER DATABASE retail OWNER TO retail_app` + transferred **2,018 tables /
   810 views / 82 sequences / 1,072 indexes / 370 schemas** to it
   (`retail_admin` left owning 0 user objects; indexes and table-linked
   sequences followed their tables automatically);
5. re-applied `superset_bi` SELECT-only grants + `ALTER DEFAULT PRIVILEGES FOR
   ROLE retail_app`; rotated the admin password into the git-ignored `.env`.

Measured `pg_stat_activity` visibility before deciding on `pg_monitor`:
superuser `7 rows / 1 state` vs an unprivileged probe `7 rows / 1 state` — no
reduction, so `pg_monitor` was **not** granted.
