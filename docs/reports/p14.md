## 1. CANDIDATE MODELS

Every dbt mart was screened against the same criteria: does the table grow
linearly with source event volume, are its rows immutable once applied, and
does a watermark detect new/updated rows without recomputing history?

| Model | Grain | Grows with volume? | Rows arrive with a detectable marker? | Candidate? |
|-------|-------|--------------------|----------------------------------------|-----------|
| `fact_ventes` | 1 row per sale line (`sale_id`) | yes | yes — per-row `ingestion_timestamp` | **yes** |
| `fact_achats` | 1 row per receipt line (`purchase_id`) | yes | yes | **yes** |
| `fact_stock` | 1 row per store/product/date | yes (snapshot cadence) | yes | **yes** |
| `dim_date` / `dim_region` / `dim_canal` | bounded (fixed or ≤ 1 row/day) | no | n/a | no |
| `dim_magasin` / `dim_client` / `dim_promotion` | bounded by catalogue/customer counts | no | n/a | no |
| `dim_produit` | product × version | low | change-detection already handled | **already incremental** (SCD2 snapshot) |

## 2. SELECTED INCREMENTAL MODELS

- **`fact_ventes`, `fact_achats`, `fact_stock` → incremental `merge`.**
  These are the only marts whose rows grow with business volume and whose
  natural key (PK in Silver) is what Silver already upserts on — so `merge`
  re-runs Silver's own idempotent semantics instead of weakening them.
- **Dimensions remain full-refresh** unless a consumer justifies change
  capture: bounded cardinality means no meaningful reuse win, and incremental
  dims would break the `grain = PK` invariant facts rely on.
- **`dim_produit` history is already incremental by construction** — the dbt
  snapshot only appends changed versions; no change needed.

## 3. WATERMARK

**Decision: the Bronze provenance `ingestion_timestamp` — strict-greater
comparison against the fact's own `max(ingestion_timestamp)`.**

- Where it lives: computed per Silver row by `add_provenance`
  (`bronze_schema.py`), stamped from `now_iso()` (`manifest.py`,
  **second precision**), refreshed on every re-promotion.
- Propagation: `stg_*` already exposed it → `int_sales`/`int_purchases`/
  `int_inventory` now carry it through → facts select it alongside their
  measures and filter `where ingestion_timestamp > (select max(...) from {{ this }})`
  inside `{% if is_incremental() %}`.
- Rejected alternatives: `event_date` (business date, not an arrival marker —
  late/corrected events behind the watermark would be silently lost),
  `source batch_id` (derived from the raw filename, coarse, cannot express a
  delta *inside* a batch).
- Granularity limitation documented: two batches promoted in the same second
  share a watermark; the loader's skip/upsert still dedupes content, but
  tests must sleep >1s between runs (the suite enforces this).

## 4. LATE-DATA STRATEGY

Behaviour is explicit and tested (see §10):

| Scenario | Mechanism | Expected result |
|----------|-----------|-----------------|
| **Late sale** (new `sale_id`, old `event_date`) | arrives with a fresh `ingestion_timestamp` > watermark | inserted as a new row on next incremental build; history untouched |
| **Corrected sale** (same `sale_id`, new values) | corrected batch re-promoted → new provenance stamp > watermark | `merge` upserts the existing row in place — same count, new values |
| **Duplicate batch** (identical file re-ingested) | Silver `already_loaded` skip prevents re-load; identical content anyway | no-op; `dbt run` idempotent on re-runs |
| **Late purchase / new stock snapshot** | same watermark rule over `purchase_id` / `(snapshot_date, store_id, product_id)` | inserted on next build |

## 8. PERFORMANCE

`benchmarks/dbt_benchmark.py` was added (mirroring the Bronze/Silver harness
style). Per scale (**100k / 1m / 5m**) it measures four phases on isolated
buckets + schemas:

1. **full** — `dbt build --full-refresh` (dims + snapshot + facts + tests);
2. **no-op** — `dbt run` on the three facts with nothing new;
3. **delta** — append 2% late sales (`--delta-pct`) with bumped watermark,
   then `dbt run`;
4. **facts full-refresh** — from-scratch facts rebuild to prove equality.

Metrics per phase: `elapsed_seconds`, `peak_rss_bytes` (psutil), calculated
`rows_per_second`; plus `pg_database_size` deltas and marts/silver schema
bytes → `benchmarks/dbt/results.json`.

**Run status: DONE (2026-10-10).** Commands run on the local stack
(Postgres 5433 + MinIO 9000), recorded in `benchmarks/dbt/results.json`:

```
uv run python benchmarks/dbt_benchmark.py --scale 100k
uv run python benchmarks/dbt_benchmark.py --scale 1m
```

| Metric | 100K | 1M |
|--------|------|----|
| Silver rows (sales/purchases/inventory) | 100,000 / 12,850 / 17,640 | 1,000,000 / 158,090 / 302,400 |
| Silver load (all sources) | 63.3 s | 1044.2 s |
| **full** `build --full-refresh` (dims+snapshot+facts+tests) | 43.1 s (130,490 rows → 3,027/s) | 76.5 s (1,460,490 rows → 19,094/s) |
| **no-op** `run` (facts, nothing new) | 23.5 s | 24.6 s |
| **delta** `run` (2% late sales) | 21.7 s (2,000 rows) | 29.5 s (20,000 rows) |
| **facts full-refresh** (from scratch) | 23.6 s (132,490 rows → 5,615/s) | 42.0 s (1,480,490 rows → 35,288/s) |
| peak RSS (dbt process family) | ≈ 157 MB (full), 154 MB (no-op/inc) | ≈ 158 MB (full), 154 MB (no-op/inc) |
| DB size after full → after incremental | 957.7 MB → 958.7 MB | 2,109.4 MB → 2,119.5 MB |
| marts / silver schema bytes | 21.5 MB / 48.2 MB | 222.4 MB / 524.8 MB |
| `equal_full_and_incremental` | **True** | **True** |
| `reconciliation_balanced` | **True** | **True** |

Read-out: the no-op incremental run costs a near-constant ~24 s of dbt
model/startup overhead at both scales (≈1.8× faster than the 100K
full-refresh build, ≈3.1× faster than 1M) — the win tracks how much history
is *avoided*, not the delta size. The 2% delta phase is dominated by dbt
startup too, so its rows/sec (92 → 677) understates steady-state throughput.
Peak RSS stays flat at ~154–158 MB from 100K to 1M, confirming the host's
~7.8 GiB RAM needs no change. Fact footprints are byte-identical between the
incremental apply and the facts-only full refresh at both scales.

The **5M** profile exists (harness supports `--scale 5m --skip-*`) but was
**not** run here, per the ~7.8 GiB-host agreement; it is provided for a later
resource-friendly run. No figures are fabricated.

## 9. CORRECTNESS

- **row counts** — `assert_fact_row_counts` (int_* vs facts) retained and
  reconciled in the benchmark (`reconciliation_balanced`, compared against
  the **post-delta** Silver counts).

  and its amount measure (`net_amount_mad` for `fact_ventes`, `total_cost_mad`

  the incremental vs full-refresh comparison is exact and order-independent

  `net`/`cost`/`margin` from the generator formulas and asserts the DB row
  equals them; measure ranges stay enforced by the retained
  `assert_fact_measure_ranges`.
- **current dimension values** — SCD2 tests (`single_current`,
  `contiguous_versions`) and the as-of joins are unchanged; late/corrected
  rows resolve the same product version as their original (tested).
- Two independent proofs: integration suite (behavioral) + benchmark
  footprint equality (scale).

## 17. WARNINGS

- **Second-precision watermark** — `now_iso()`; two promotions in the same
  second share a watermark (content still deduped by Silver/merge, but
  tests must sleep >1s — the fixture does).
- **`ingestion_timestamp` is provenance, not business time** — document for
  BI consumers; never join `dim_date` on it.
- **Incremental tables are stateful** — the documented reset path is
  `dbt run/build --full-refresh`; a dropped fact table rebuilds from Silver.
- **`fact_stock` now carries business-key columns** (for merge) — additive,
  but consumers may confuse them with dim attributes.
- **Host constraint** — 5M benchmark provided but not run on this ~7.8 GiB
  RAM host; 100K/1M used per agreement.
- **Benchmark harness hardened during live verification** — three latent
  defects (never exercised until `.env` existed) were fixed: `_fact_footprint`
  unpacked a 3-column row into one variable, and assumed every fact had
  `net_amount_mad` (now per-model `FACT_MEASURES`); the RSS sampler only
  polled after each 64 KB of output so small builds logged `0 B` (now a
  drain thread + 0.1 s sampling); and `reconciliation_balanced` compared
  post-delta fact counts against **pre-delta** Silver counts (now
  `silver_counts_after_delta`, with explicit fact↔silver key mapping). See §12.
- **README consistency** — the phase banner is now Phase 16; no Phase-14
  README edit is required.

## 21. RECOMMENDATIONS

1. **Keep the `ingestion_timestamp` watermark + `merge` strategy** — it
   reuses Silver's own idempotent semantics and makes the common no-op day
   cost a near-constant ~24 s of dbt overhead (measured, §8).
2. **Add a cheap "nothing new upstream" gate** in the Airflow dbt task
   (e.g. compare Silver `max(ingestion_timestamp)` to the fact max before
   running `dbt run`) to skip the no-op phase cost on quiet days.
3. **Surface applied-delta telemetry** — have the orchestration task log
   `delta_rows` from the benchmark harness per daily run.
4. **Re-run the benchmarks after any change to the fact paths** or after a
   Postgres major upgrade, and track `benchmarks/dbt/results.json` over time
   (it now stores per-model footprints and post-delta Silver counts).
5. **Revisit incremental dims only if a consumer demands it** — currently
   unjustified; `dim_produit` is already incremental via the snapshot.
6. **Document `ingestion_timestamp` semantics** for Superset consumers, and
   protect the merge keys (`sale_id`, `purchase_id`,
   `(snapshot_date, store_id, product_id)`) in the mart catalogue.
